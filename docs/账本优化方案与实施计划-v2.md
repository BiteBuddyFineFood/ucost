## 二、产品规则

### 2.1 分类与图标

1. 购物物品增加“支出分类”，支持单项选择、批量修改、AI 建议。只允许选择当前用户可用的支出分类；未分类仍可保存和记账，但在确认面板明显提示。
2. 物品转为支出时默认继承物品分类，允许在确认面板更改；提交后的选择回写物品，并写入对应账单。清单不是分类：同一清单里的食品、交通、数码可分别属于不同分类。
3. 修改已购项的分类时，若仍有关联账单，展示“同步修改关联账单分类”，默认勾选；同步必须校验两个对象的版本并在同一事务中完成。普通修改清单名称或说明不会改变账单分类。
4. 账本提供“未分类”筛选和“AI 分类”批量按钮；默认只选未分类记录，已分类记录需用户主动选中才参与。购物物品可复用该能力。
5. AI 返回“标题、原分类、建议分类、简短依据、待核对原因”，用户可逐条改选、取消、确认。只应用分类字段，不改变日期、金额、账户、备注。
6. 分类规则优先于模型建议；只允许已有且类型匹配的分类 ID。没有合适分类时保留未分类，并提供手动创建入口，不自动创建分类。转账不参与分类；退款继承原支出分类，通过原支出修改。
7. 每个收入/支出分类支持选择内置图标和颜色，沿用已有 Lucide 图标库，首版不要求上传图片。图标以稳定标识存储，未知标识降级为通用图标；旧分类自动使用默认图标。
8. AI 建议保存后刷新仍可查看。确认时检测记录版本和分类是否归档，过期建议不覆盖用户后来做出的修改。

### 2.2 原页面暂存与待整理归属

统一术语：暂存记录是原始输入，整理结果是待确认候选，确认后才产生正式账目或物品。未确认内容不计入收入、支出、省钱和账户余额。

各页面增加“暂存记录”区，默认展示未整理、整理中、待确认和失败记录，可折叠；已完成记录进入历史筛选。

| 页面 | 展示的暂存范围 |
| --- | --- |
| 账本 | `target=ledger` |
| 购物清单总览 | `target=shopping`，标明各自清单 |
| 某一购物清单 | `target=shopping` 且 `targetListId` 为该清单 |
| 省钱本 | `target=savings` |
| 物品成本 | `target=items` |
| 待整理 | 所有模块，另含自动判断和普通文本 |

- 卡片展示原话/附件摘要、采集时间、状态、目标位置，以及修改、整理、确认、忽略入口。例如“购物清单 / 双十一采购 · 未整理”。
- 在清单内口述保存后，立即在该清单出现；切换到另一个清单后确认，也不能改变原草稿的归属。
- `auto` 显示“待判断归属”，`text` 显示“普通备忘”。自动判断已产生多模块候选时，在待整理卡片标明候选分布；各模块可显示相关候选入口，但仍引用同一草稿，不能复制数据或重复统计。
- 待整理支持模块、清单、状态筛选；顶部显示分区数量，批量整理范围与当前筛选和显式选择一致，不暗中处理其他分区。
- 未应用任何候选的草稿支持修改原话、目标模块和目标清单；修改后清除旧候选/旧错误并返回未整理，保留原采集时间，另记录更新时间。
- 正在整理时暂不允许修改；任务完成后可修改再整理。已部分确认时，剩余候选可编辑，原话保持可追溯；要重写原话则建立补充草稿，已确认记录从业务页面修改。
- 目标清单被归档/删除时显示异常归属，要求选取可用清单后再确认，不自动转到当前清单。
- 额度用完、AI 未配置或识别失败，都不影响暂存和修改。提供“手动整理”入口，人工填写候选后也能走统一确认流程。

### 2.3 分组视图与平铺视图

采用独立的“记录组”，用于表达一次采购、旅行或其他活动。一个组可包含不同日期的账单和省钱记录；日期仍是各条记录自己的业务日期。

- 账本、省钱本各增加“分组 / 平铺”切换，偏好分别按用户保存。
- 购物清单首次记账时自动建立对应的记录组，名称默认与清单一致，以清单 ID 绑定，不能通过名字匹配。同名清单仍是不同组。
- 之后该清单的记账和关联省钱进入同一组；清单改名同步组名。清单删除后保留组及最后名称，账目和省钱记录保留，标明来源清单已删除。
- 支持手工创建组、批量移入/移出组、解散组。清单来源组的调整需预览清单关联影响；组名称在来源清单中修改，手工组可直接改名。
- “切换为平铺”只改变展示；“移出组”改变归属；“解散组”解除全部成员的分组，不删除账目。这三个动作使用不同入口和文案。
- 来源关系独立于展示分组：用户把账单移入旅行组后，原购物清单仍能找到该账单，预算仍按来源关系计算。
- 无组记录在分组视图里放入“未分组”。组标题展示名称、日期范围、记录数和本页筛选范围内的小计；收入、支出、退款分列，净支出=支出−退款。
- 先应用日期/分类/账户筛选，再分组。跨月的组在某月页面只汇总该月匹配的记录，并标明“当前筛选小计”；点击查看全组可看完整范围。
- 分组分页以组为单位，组内记录按需展开和加载；平铺按记录分页，避免在一页显示不完整组却误报全组总额。
- 省钱组汇总只计算有效记录，待核对、撤销和被整单结算替代的记录不计入总额。

### 2.4 清单预算、全部记账和预算结余

**预算设置**

- 清单新增可选“总预算”；未设置时显示“未设置预算”，零预算与未设置要区分。
- 物品预算继续保留。提供“用物品预算合计填入总预算”按钮，执行一次性复制；之后编辑物品预算不悄悄改变总预算。
- 清单头部显示总预算、已购实付、已关联账本金额、退款、预算余量及未购数量。“已购未记账”独立提示，不能把删除账单后的已购项当成免费购买。
- 总预算是用户自定控制线，不强制覆盖实付；超预算仍可记账，显示超支金额，不生成负省钱记录。

**全部记账**

按钮命名为“全部记账”，打开逐项核对面板后才提交。面板明确区分未购买、已购未记账、已入账、已放弃四种情况：

1. 未购项可在本次确认已购买；已购未记账项用于补记；已入账项标记“已记账”并跳过；已放弃项默认排除。
2. 每项展示实付、日期、分类、账户、优惠、是否建立物品档案。可以设置统一日期/账户，再逐行覆盖。预算只作参考，不自动当成实付；实付未知必须填写。
3. 没买的条目可取消选择，仍保留在清单中。免费获得的物品允许标记已购和建立零成本档案，但不生成不符合现有正金额规则的零元支出。
4. 提交前显示本次新增多少笔支出、合计多少、分入哪个组、是否产生省钱记录。
5. 一批最多 100 项，全量校验归属、版本、金额和有效关联后事务提交。重复点击、网络重试、不同请求同时买入同一项，都不能重复记账。超过上限要求分批，整单预算结算待全部批次核对完成后执行。
6. 已购未记账项补记时优先关联已有物品档案，不重复创建。若疑似已有手工账单，可由用户选择关联，经校验后跳过新建。

**预算结余如何记入省钱本**

为避免一份优惠既按商品记入省钱、又包含在总预算结余中，清单提供互斥的省钱核算方式：

| 模式 | 省钱记录规则 |
| --- | --- |
| 按商品记录（兼容旧数据，默认） | 沿用优惠、不买、降级购买的现有规则，物品间分别记省钱 |
| 按整单预算结算（用户主动选择） | 同一清单只将确认后的总预算结余计入省钱；商品优惠等明细保留作解释，不再额外累计 |

- “全部记账”面板可勾选“完成清单后，将预算结余记入省钱本”，展示将使用整单预算模式及对既有省钱记录的影响。
- 结算前要求所有条目已购买或已明确放弃，没有未核对实付；用户确认本轮采购已结束。仍有待购物品时只显示预算余量，不提前记成省钱。
- 首版采用保守口径：预算结余 = `max(总预算 − 本轮已购实付合计, 0)`。退款单独展示，不自动当成新增省钱；要调整本轮采购范围时重新核对结算。
- 生成一条“XX 清单预算结余”省钱记录，类型为 `budget_surplus`，来源为清单结算，进入该清单组，记录预算快照、实付快照和结算日期。
- 示例：总预算 1,000 元，实付 800 元，其中优惠 50 元。整单模式只统计 200 元；优惠 50 元保留为解释，不能再把总省钱算成 250 元。
- 切换为整单模式时，列出该清单已存在的优惠/降级/放弃省钱记录，将系统派生且属于本轮采购的记录标记为被结算替代。用户已手动删除或停用的记录保持停用；无明确来源的手工省钱不自动改动，需用户明确其是否属于同一结算，否则阻止产生可能重复的结余。
- 重新打开清单、变更预算/购买金额/购买状态、发生退款或删除关键账单后，已有预算结余标为待核对，暂停计入有效省钱；用户重新确认后更新同一结算的记录，不重复新建。
- 切回按商品模式时撤销预算结余，并依据当前有效账单和原停用意图恢复应计商品省钱，预览后事务提交。
- 首版一张清单对应一轮预算结算。重复周期采购使用“复制为新清单”，避免历史结算被下一次采购覆盖；周期清单多轮结算可后续扩展。

### 2.5 已购项修改与账单删除修复

购买状态表示商品是否买过，入账状态表示有没有有效账单，两者分开。

| 购买状态 | 有效账单 | 页面展示与操作 |
| --- | --- | --- |
| 考虑中/待购买 | 无 | 修改、买到了、放弃 |
| 已购买 | 有 | 修改购买信息、查看账单、撤销购买 |
| 已购买 | 无 | “已购·未记账”，修改购买信息、补记账、撤销购买 |
| 已放弃 | 无 | 修改说明、恢复待购；已生成的放弃省钱随恢复撤销 |

- 删除支出默认保留“已购买”事实，清空有效关联并展示“账单已删除，可补记账”；删除面板给出关联影响摘要。需要改回待购时使用明确的“撤销购买”操作。
- 删除前保存购买金额、日期等必要快照；后续补记直接预填快照，旧数据缺失时要求用户补齐，不拿预算代替实付。
- 修改已购金额/日期且有关联账单时，显示账单、优惠省钱、物品成本和整单预算结算的影响，一次事务同步；没有账单时修改购买快照。
- 撤销购买显示将删除的账单、撤销的系统派生省钱、保留或解除关联的物品档案；已使用物品不得静默删除。有关联退款时先处理退款，沿用现有约束。
- 购物决定产生的降级/放弃省钱也要纳入同步，不能只处理 `source=automatic` 的优惠记录。没有足够来源信息的旧记录进入待核对，不猜测删改。
- 服务端允许合法恢复流程，但不通过普通 PATCH 任意改终态。增加专门的修正、补记、撤销动作，统一维护所有关联。

### 2.6 可选账户与默认账户

- 新增“默认支出账户”，设置页可选任一未归档账户，也可选择“不设置”。
- 新支出、购物单项入账、整单记账和 AI 支出确认都预填默认账户，用户每笔可覆盖或主动清空。
- 请求未提供账户字段表示可使用默认值，显式 `null` 表示用户选择不指定。已有记录编辑时未提供字段应保持原值，不能被新默认账户覆盖。
- 无账户支出仍计入总支出，但不改变任一账户余额；摘要可展示未指定账户的金额，便于核对。
- 默认账户归档时清除默认设置，历史关联保留；导入旧记录时缺失账户保持空，不套用当前默认账户。
- 收入账户保持独立选择；转账仍必须指定两个不同账户；退款按原账单及退款规则处理，不套用默认支出账户。

### 2.7 AI 页面、个人配置和每日额度

**页面表达**

- 普通业务页面只显示“AI 整理”“AI 分类”“系统服务 / 个人配置”“今日剩余次数”等，不显示系统模型名称或供应商内部信息。
- 设置页提供折叠的“自定义 AI 服务”，包含接口地址、密钥、文本模型、可选图片模型、连接测试、启用/停用。用户需要在这个配置表单里填写和查看自己设置的模型名，其他业务页面不展示。
- 系统服务沿用服务端环境配置；启用有效个人配置后走个人服务，不受系统每日 10 次额度限制。个人服务失败不自动回退系统服务，以免暗中扣次数；可由用户明确切换。
- 若未启用个人配置且部署未配置系统服务，展示暂不可用，继续支持暂存与手动整理。

**推荐计次口径**

每日 10 次按“用户发起的一项 AI 任务”计算，所有使用系统 AI 的入口共用额度，避免换一个入口就绕过限制：

| 操作 | 计次建议 |
| --- | --- |
| 整理一条或一批草稿（每批最多 10 条） | 1 次任务；内部逐条调用不重复扣次 |
| 批量分类（每批最多 50 条） | 1 次任务，超过上限拆成明确的新任务 |
| 表单建议、润色、统计分析 | 每次用户任务 1 次；内部多阶段调用合并计费 |
| 手动编辑、确认候选、查看已保存结果 | 不计次 |
| 同一任务网络重试或读取进度 | 不重复计次 |
| 完全失败、未产生可用结果 | 释放预占，不扣次数；仍有请求频率限制 |
| 批次部分成功 | 计 1 次；失败项在同一任务内最多重试 1 次，不再扣；之后需显式创建新任务 |
| 系统服务连接状态检查 | 不调用付费推理，仅检查配置/健康状态 |
| 个人配置连接测试 | 走用户配置，单独限频，不扣系统额度 |

- 日期采用服务端固定业务时区 `Asia/Shanghai`，每天 00:00 重置；展示重置时间。修改用户时区不能额外获得额度。
- 调用前原子预占，保证“已使用+预占 ≤ 10”；任务结束成功消费预占，完全失败释放。并发标签页也不能超额。
- 自动整理与手动整理共用配额；耗尽时停止自动触发，保留队列，不连续弹错或重试。
- 批量任务固定草稿/记录 ID 和版本，包含运行步骤、输出、过期时间和执行租约；客户端不能向已扣费任务无限追加内容。任务建议有效期 24 小时，跨日重试仍归原任务额度日期。
- 超时任务先停止/确认失效再释放预占；租约已失效的迟到响应不能再次写入和扣费。限制最大文本、图片数量/大小、输出 token 和并发数，防止一次任务无限扩张。
- 配置密钥仅服务端加密保存，API 返回掩码/是否存在，不回传明文，不写日志、业务快照或导出。加密主密钥由服务端环境配置管理。
- 自定义地址是服务端出站请求：生产环境校验 HTTPS，限制内网/回环/云元数据地址，控制重定向并防 DNS 重绑定；本地模型如需开放 localhost，通过部署级明确选项允许，不能让普通用户任意访问服务器内网。

### 2.8 新版导入导出

当前不存在导入器，因此这部分包含新增导入流程，不只是修改导出列。

**导出格式**

- JSON 升为 `schemaVersion: 2`：包含账户、分类及图标、分组、账本、清单及预算/购买快照、省钱及结算关联、草稿及已有其他业务数据。
- 增加 `datasetId`、导出记录稳定 ID、格式版本、导出时间、币种 `CNY` 和金额单位 `cent`。JSON 金额继续使用整数分。
- 账本 CSV v2 至少包括：版本、来源数据集/记录 ID、日期、类型、标题、实付金额（分）、账户 ID/名称、转入账户 ID/名称、分类 ID/名称、组 ID/名称、来源清单/购物项 ID、退款来源 ID、优惠及优惠前金额、自动省钱开关、订单标识、备注。
- 省钱本 CSV v2 至少包括：版本、来源数据集/记录 ID、日期、标题、类型、来源、计划金额（分）、实际金额（分）、省下金额（分）、组 ID/名称、来源清单/结算/账单/购物项 ID、有效状态、停用标记、来源唯一标识、备注。
- 分类图标、完整结算快照和其他模块复杂关联以 JSON 完整承载。CSV 负责账本/省钱本交换，不宣称一个 CSV 能恢复整个应用。
- 分组和平铺只影响显示，导出始终一条正式记录一行，组信息作为字段，不导出会被误导入为账单的汇总行。提供“全部数据 / 当前筛选范围”，默认明确。
- 沿用 UTF-8 BOM、引号和换行转义、公式注入防护；机器导入要有版本化可逆转义约定，确保原始以 `=`、`+` 等开头的文本回导不变。
- 不导出密码、会话、AI 密钥、配额内部凭据或有效分享 token。草稿可包含附件元数据，但 JSON 不包含二进制附件；缺少附件时显示“附件未迁移”，不能显示已恢复图片。完整附件恢复继续使用明确的文件备份流程。

**导入流程**

选择文件 → 识别版本和列映射 → 校验与关联映射 → 预览新增/重复/冲突/错误 → 用户确认 → 事务导入 → 结果报告。

- 支持 JSON v1/v2、旧版账本 CSV、账本/省钱本 CSV v2。旧 CSV 没有分类/账户/组则保留为空，未识别字段不猜测填值。
- 所有导入数据归当前用户；源 ID 映射为本地 ID，不信任文件内 `ownerId`。账户/分类按明确映射或创建处理，组优先按数据集和源 ID 匹配，同名不同来源不自动合并。
- 导入 v1 时执行与数据库升级相同的关联回填规则；默认图标和未分组补齐，无法恢复的购买信息标待核对。
- 第一版默认“合并新增、不覆盖现有数据”。按数据集+源实体 ID 去重；v1 缺少数据集时使用可确认的来源标识和旧 ID，不能仅凭标题/金额判定同一条。相似账单只提示。
- 明确区分重复与冲突：同一来源记录且内容一致可跳过；内容变化需用户选择保留现有或作为新记录，不静默覆盖。重试同一导入任务不能再次落库。
- 缺失退款原单、跨用户引用、已失效分类、缺少结算成员、重复自动省钱等必须在预检标出；需要的源记录不在文件里时允许映射已有记录，无法解决时不允许确认受影响部分。
- JSON 完整导入按来源关系恢复已有派生省钱，禁止再次运行自动派生导致翻倍；账本 CSV 若允许自动生成省钱，须在预览中明示。随后导入省钱 CSV 按来源键识别已有派生记录。
- 导入不发起 AI 请求，不消耗额度，不套用当前默认账户；不恢复可用登录态、公开分享链接或执行中的 AI 任务。中断草稿恢复为可重试状态，已确认索引要与导入的正式记录核对。
- 首版设置单文件体积及记录数上限，在事务前完整预检，超限要求拆分；不悄悄分块造成部分导入却显示成功。大体积附件备份仍走原备份方案。

## 三、数据结构与服务设计

### 3.1 建议的增量数据模型

下面为实现建议，最终字段名可随项目规范调整，但职责和约束不可省略。金额统一整数分，引用必须校验同一用户归属。

| 实体 | 建议增量 | 关键约束 |
| --- | --- | --- |
| `Category` | `iconKey`、`color` | 图标/颜色白名单；未知图标回退；保留现有分类唯一约束 |
| `User` | `defaultExpenseAccountId?`；preferences 内独立保存两个视图偏好 | 默认账户必须属于用户且未归档 |
| `RecordGroup`（新增） | ownerId、name、sourceListId?、archived、version、时间 | 来源清单唯一绑定；手工组无来源；名称不作为关联键 |
| `ShoppingList` | `budget?`、`savingMode`、`closedAt?` | 未设预算与零预算不同；旧清单默认按商品核算 |
| `ShoppingItem` | `categoryId?`、`purchaseAmount?`、`purchasedAt?`、`purchaseAccountId?`、`purchaseDiscount?`、`purchaseRevision`、购买信息待核对标记 | 状态与入账分开；购买快照在删除账单后保留；复用 ledgerId/ownedItemId |
| `LedgerEntry` | `groupId?`、`sourceShoppingItemId?` | 购物来源与展示组分开；首版同一购物项最多一个有效主支出；退款沿 refundOfId 关联 |
| `SavingEntry` | `groupId?`、`sourceListId?`、`settlementId?`、`supersededBySettlementId?`；新增类型 `budget_surplus` | 被结算替代与用户主动 suppressed 分开；所有汇总统一排除无效/被替代项 |
| `ListSettlement`（新增） | ownerId、listId、预算/实付快照、成员摘要、状态、confirmedAt、version | 首版每清单一份当前结算；修改重新确认更新同一记录；成员摘要用于检查过期 |
| `CaptureDraft` | `updatedAt`；继续复用 target/targetListId/result/appliedIndexes | 不建立“各页面草稿副本”；已应用索引不可重复确认 |
| `UserAiConfig`（新增） | ownerId、enabled、baseUrl、加密密钥及加密版本、模型配置、version | 每用户一份；与普通 preferences 和 snapshot 分离 |
| `AiDailyUsage`（新增） | ownerId、quotaDate、reserved、used | ownerId+quotaDate 唯一；事务预占与结算 |
| `AiTask`（新增） | ownerId、kind、providerMode、quotaDate、固定输入/版本、步骤进度、结果、状态、operationId、lease、expiresAt | 用户+operationId 唯一；步骤重试次数有限；分类建议可恢复 |
| `ImportJob` / `ImportIdentity`（新增） | 用户、预检摘要/文件哈希、状态；datasetId+entity+sourceId → localId | 预检不可篡改；来源映射唯一；重复提交幂等 |

数据库约束与服务校验同时使用：增加 ownerId+groupId/date、ownerId+target/targetListId/state 等查询索引；有双向关联时在同一事务维护。迁移前检查旧数据是否存在一对多冲突，不能直接加唯一约束后让升级失败。

### 3.2 服务与接口

保留当前登录、`operation()` 幂等封装、版本校验和事务模式，把新增职责抽成独立服务，避免继续堆入一个超大文件。

| 服务 | 主要职责 | 建议接口/动作 |
| --- | --- | --- |
| 分类服务 | 图标、购物分类继承、批量建议及确认 | `POST /api/classification/preview`、`/apply` |
| 草稿服务 | 按模块查询、修改归属、统一确认 | 扩展 `draftEdit`，复用 `/api/capture`、`/process`、`/apply` |
| 购物服务 | 购买修正、补记、撤销、整单记账 | `purchaseEdit`、`purchaseUndo`、`shoppingRelink`、`listCheckout` |
| 分组服务 | 创建/改名、批量移入移出、解散、筛选汇总 | `groupSave`、`groupAssign`、`groupDissolve` |
| 结算服务 | 预算预览、方式切换、结算确认、失效与重算 | `listSettlementPreview`、`listSettlementConfirm`、`listReopen` |
| AI 网关 | 选择系统/个人配置、额度、限流、执行和重试 | `/api/ai/config`、`/test`、`/usage`、`/tasks/:id` |
| 数据交换服务 | v1/v2 解析、ID 映射、预检与导入 | `/api/export` 扩展；`POST /api/import/preview`、`/commit` |

- 路径是建议，不强制把现有 mutate 风格全部改为 REST；领域服务是唯一写入入口，手动表单、AI 确认、批量操作和导入共享校验。
- 所有有副作用的确认操作带 operationId 和版本；预览只计算，不改业务数据。提交重新核验预览所依赖的记录，过期返回具体冲突。
- AI 网络请求放在数据库事务外；短事务只做领取、预占、结果落库和额度结算。SQLite 写入竞争需有限重试，不持锁等待模型响应。
- 统一改造 `suggest`、`processDraft`、`analyze`、`polish` 和连接测试，避免只有新按钮受额度控制，旧接口仍能绕过。
- 当前快照返回全量数据；先补齐新实体和兼容字段，再为组列表/草稿列表引入服务端筛选分页。所有页面、导出和 AI 汇总共用同一有效省钱计算函数。
- 实施前按 AGENTS.md 阅读本地 `node_modules/next/dist/docs/` 对应 Route Handlers、服务端/客户端边界指南，按安装版本实现，不照搬旧 Next.js API。

## 四、实施步骤与交付顺序

### P0：数据保护和购买状态修复

交付：用户报告的 bug 可复现、可验证修复；已有财务汇总不因迁移自动变化。

### P1：分类、账户和暂存体验

交付：清单分类可继承入账；暂存原地可见可改；未指定账户仍可记账；默认账户各入口一致。

### P2：记录组、整单记账和预算结算

4. 将退款、删除、修改购买信息、移动分组和清单归档/删除纳入联动验证。

交付：跨日期记录可属于同组；整单记账可重复安全提交；预算省钱不与优惠重复累计。

### P3：用户 AI 配置、统一配额和批量分类

4. 完成桌面/手机主流程验证，更新 README、`docs/PROGRESS.md` 和迁移/回退说明。

交付：新格式可往返恢复关键业务字段及关联；旧格式可明确降级导入；给出实际验证证据。

## 五、升级和历史数据处理

1. 使用新增迁移升级，禁止重建/重置现有数据库。迁移先添加可空字段或兼容默认值，再回填，最后添加必要约束。
2. 分类图标补默认值；默认账户为空；旧清单预算为空，保持按商品核算；视图偏好初始可沿用平铺，避免升级突然改变用户使用习惯。
3. 从 `ShoppingItem.ledgerId` 的有效引用回填账单购物来源与购买快照；按真实 `listId` 建组。通过购物项/关联账单识别的省钱记录回填同组，不能靠同名或相同金额匹配。
4. 已购无账单、账单已删或多个购物项异常引用同一主支出的历史记录输出修复报告；无法唯一判断的不自动建立关联、不自动补支出。
5. 原有自动优惠、用户主动停用标记、退款关系、已确认草稿索引保持；迁移不产生任何新的省钱金额。
6. 数据库升级演练分别使用空库和现有库副本；核对记录数量、收支总额、有效省钱总额、关联完整性及用户隔离。
7. 回退采用匹配版本的代码+数据库备份，不能直接让旧代码写入已经使用新业务字段的数据。上线前约定维护窗口；上线后若有新写入，需先保存新数据再进行恢复，明确可能的数据恢复范围。
