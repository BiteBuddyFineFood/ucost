# UCost 全量迁移 Cloudflare：实施与交接方案

日期：2026-11-12。状态：方案已编写，尚未实施或验证 Cloudflare 迁移。

## 1. 目标与授权边界

将现有应用整体迁移到 **Cloudflare Workers + D1**。保留 Next.js 项目结构、React 页面、TypeScript、手绘 UI 和已有业务功能，优先完成可在本地 Workers 环境运行的版本。以后网站、接口与数据库统一放在 Cloudflare。

用户量很少，以个人使用为主。不为假设的大流量引入微服务、消息队列、分布式锁、复杂缓存或全面分页重构。只处理平台实际限制、基本数据一致性和已有访问权限要求。

本文件交给执行 AI 后，可按阶段持续修改项目、安装必要依赖、运行本地迁移及测试。不要只做方案或静态页面。普通实现选择自行处理，阶段完成后记录实际证据。

本地实施阶段不注册账号、不创建云端资源、不部署、不购买服务、不启用付费套餐、不自动提交 Git。云端部署说明可以准备好，但实际发布留给用户另行授权。

### 用户已确认的产品调整

- **截图仅用于识别，不作为账单附件长期存储。** 新截图在当前请求内识别，应用只保存文字、结构化候选、时间和模块信息；不写入本地文件、D1 BLOB、R2 或其他持久存储。
- 截图可以保留在当前浏览器页面内存中用于失败重试；关闭或刷新页面后需要重新选择图片。不要暗中使用 localStorage / IndexedDB 留存图片。
- 原来的“先存着，累计 5～10 条整理”继续支持文字和口述。带截图时明确提示须先识别，识别结果可稍后确认，不能承诺关掉页面后还能识别未保存的原图。
- AI 仍只做识别、表单整理、分类建议和统计解释，不做聊天助手。
- 当前模块可查看已保存的 AI 草稿；待整理明确显示所属模块，购物草稿显示目标清单。仓库已有相关实现，保留并验证，不另做一套。

## 3. 目标架构与选型规则

```text
电脑 / 手机浏览器
    │ 同源 HTTPS
Cloudflare Workers
    ├─ 现有 React / Next.js 页面与静态资源
    ├─ 现有业务 API、会话、权限校验
    ├─ D1 数据访问层 → 云端 D1
    └─ AI 网关 → 用户已配置的模型 API

本地：对应构建工具 + Wrangler/workerd + 本地 D1
```

### 3.1 Next.js 运行方式

先做小范围兼容性验证，再选定一种构建方案。

- 官方 Next.js 指南在本方案核对时推荐 **vinext**，同时明确其仍为 beta；它重实现 Next.js API，不能描述成完全不改变构建链的插件。
- **OpenNext Cloudflare** 也是候选。核对其当前支持的 Next.js / React 版本、构建方式和限制，不能假定一定支持本项目安装版本。
- 按“保留现有功能、改动少、可复现验证”选择一种，记录选型原因与锁定版本。不要同时维护两套 Cloudflare 构建链。
- 不预先降级 Next.js / React，不为了部署改写成 Hono 或静态站。只有明确兼容问题才做最小版本调整，并写明证据和影响。
- 使用工具当前要求的 compatibility date、兼容标志和 binding 获取方式。不要凭记忆编造配置。
- 不把 `runtime = 'nodejs'` 简单替换成 `edge` 就宣称迁移完成；`maxDuration = 120` 也不能当作 Workers 的执行时长保证。

### 3.2 D1 数据访问

默认采用 **Drizzle 的 D1 驱动及显式批处理**。原因是现有 Prisma 交互式事务无法原样迁移，而项目还使用了 Prisma 模型元信息；直接建立清晰的 D1 数据层比模拟完整 Prisma API 更容易维护。

若执行时验证 Prisma 官方 D1 适配器确实能显著减少改动，也可以保留 Prisma；必须实际验证本项目版本、日期/布尔类型、迁移和批量写入，且不能继续依赖不支持的交互式事务。完成第一阶段后确定唯一主路径，不长期维持两套线上 ORM。

- 本地与线上使用相同 schema、查询和迁移，只切换 D1 binding 对应的本地/远端数据库。
- 旧 Prisma/SQLite 工具可暂留作只读导出与迁移辅助，不必继续维护旧数据库作为另一套正式运行后端。
- 保留整数分金额、ID、日期语义、已有唯一约束、归属字段及必要索引。
- 不创建巨大的“兼容 Prisma”代理层，也不要逐个路由直接散落 SQL。按现有领域建立小型数据访问函数。

### 3.3 多表保存与失败处理

不保留复杂交互式事务结构。通常先读取和校验、生成 ID，再把相关写入放入 D1 `batch()`。D1 batch 是顺序执行且失败回滚的一批 SQL。

必须共同成功的场景包括：购物入账及关联省钱/物品、退款关联调整、AI 候选确认、需要保持完整性的批量编辑和删除。现有操作 ID 和唯一约束用于避免重复提交，不另外设计分布式系统。

注意：`UPDATE ... WHERE version = ?` 影响 0 行并不等于 SQL 抛错，不能假定 batch 自动回滚；涉及条件写入时，要让后续写入依赖成功条件或使用约束保证，检查实际变更结果。不要在部分写入已提交后，仅向用户返回“冲突”却留下残缺数据。

无需为假设的大并发扩展架构，但保留已有用户隔离、重复提交保护、评议人数规则和 AI 额度正确性。

## 5. 五个执行阶段

### 阶段一：兼容性验证与路径确定

1. 保存当前基线的检查结果，区分已有错误和迁移引入的错误。
2. 核对适配工具官方文档，完成版本支持检查并选型。
3. 在本地 Workers 运行环境打开现有首页与登录页；验证 Cookie 读写和 API 路由。
4. 配置本地 D1，跑通建表、读取、写入、batch 失败回滚。不得连接或改写远端数据库。
5. 对登录密码计算、AI 网络实现和导入器做针对性兼容检查。只处理实际失败，不扩大成性能重构。

产出：可复现命令、适配工具版本、已通过/失败项及数据库方案。此阶段页面能打开不代表迁移完成。

### 阶段二：D1 schema、业务数据层和迁移

1. 覆盖 schema 中所有业务表，包括账户、分类、账单、清单、物品、使用记录、省钱、记录组、结算、个人 AI 配置、AI 任务/额度、草稿、导入身份/任务、评议和操作防重。
2. 迁移 CRUD、查询统计和多表保存；金额统计继续由程序/SQL 计算，不交给 AI 算账。
3. 将 `Prisma.dmmf` 依赖改为明确、可维护的字段元信息或所选 ORM 支持的方式；禁止靠删字段让导入导出表面通过。
4. 根据现有 SQLite 副本生成可重复导入的 D1 数据。处理日期、布尔、空值、唯一值、JSON 文本和记录间引用。
5. 本地 D1 重启后验证数据持久化；重复迁移不会重复创建业务记录。

数据保护与迁移规则：

- 操作旧库前做一致备份（停止写入或使用 SQLite 备份机制，不能忽略 WAL 直接复制活跃库）。源库只读，测试只写副本/独立本地 D1。
- 比较迁移前后各表数量、收支与省钱合计、购物关联、分组、结算、草稿状态和导入身份映射。
- 保留原有用户归属和密码哈希。旧会话可选择失效并要求重新登录，但必须说明。
- 个人 AI 密钥若已加密，迁移密文时必须保留对应的加密配置；不能解密后写入普通导出文件或日志。
- 旧附件不上传云端、不自动删除原始文件。已识别草稿保留结果；仍依赖旧截图的未识别草稿标记“需重新选择截图”，不能悄悄丢掉这部分输入后显示成功。

### 阶段三：AI、截图与登录适配

#### 截图流程

```text
选择/粘贴截图（浏览器内存）
 → 校验类型与大小
 → 请求内调用识别 API
 → 校验结构化结果
 → 保存文字/候选、采集时间、模块、目标清单
 → 用户在当前模块或待整理中确认
```

- 不保存图片字节、base64 或 data URL 到草稿、AiTask、提示词日志、错误日志、缓存或数据库。检查全链路，而非仅删掉 `writeFile`。
- AI 请求仍由服务端携带密钥发出。截图会发送给用户配置的识别服务；“应用不留存”不代表能保证模型供应商不留存。
- 失败显示真实错误，浏览器仍保留待重试文件；未识别图片不得伪装为已持久保存。
- 采集时间在本次输入时固定，不随重试或稍后确认而改变；一次输入多图仍遵循明确的草稿/候选关联。
- 只有文字时保留“先存着”、手动整理、累计 5～10 条触发及当前模块查看功能。
- 批量识别避免整个任务只能在一次长请求中完成；复用现有按草稿处理/进度机制。无需增加队列产品；用户关闭页面时，不宣称进程必定继续运行。
- 保留结构化结果校验、修改候选、重复提醒、确认后入账、优惠关联省钱和重试防重。

#### AI 网关

- 检查 `AsyncLocalStorage`、加密、DNS、`node:http`/`node:https` 的兼容性。可兼容的部分保留，不批量改写所有 `node:*`。
- 自定义模型地址原先做了 DNS 校验和连接地址固定。改成标准 `fetch` 时不能直接删掉这些保护后接受任意地址；优先用明确的可信供应商地址列表或经过验证的等效限制，具体差异写入文档。
- 保留系统/个人配置、任务状态、额度预留与释放、超时恢复；失败不能留下永远整理中的草稿。
- 本地测试默认使用确定性 AI 替身，不伪装真实模型验证。真实调用仅在已有授权和可用配置下做小样本测试，不在日志输出密钥或个人数据。

#### 登录

- 保留登录、Cookie 和用户隔离。原密码哈希不得直接丢弃；不可为了适配免费 CPU 限制改成普通 SHA256 或大幅削弱密码强度。
- 检查现有 bcrypt cost=12 的实际运行兼容性。可考虑安全的原生 Web Crypto 实现/受支持方案，但须明确旧密码兼容或迁移机制。
- 不把进程内 Map 当作线上持久限流保证；按当前单用户规模做最小可靠实现，不扩展成复杂风控。
- 本地模拟能运行不能证明满足云端免费 CPU 限额；如果需要云端测量，记录为待部署验证，不擅自开通付费套餐或删掉登录功能。

### 阶段四：导入导出及完整回归

保留 JSON v2、账本/省钱 CSV v2、旧格式导入、预检、字段/身份映射、冲突选择、来源关联和重复导入保护。

- 常规个人规模直接处理，不预先增加复杂任务调度。
- 根据 D1 实际参数、语句和请求限制确定支持的导入大小。必要时调整写法，或在任何写入前明确拒绝超限文件。
- 现有导入承诺整批原子性：不能简单分几批提交，却仍显示“整批失败未导入”。如果必须分批，要明确进度、恢复与幂等语义，并记录行为变化。
- 导出器不能因分次读取产生明显不一致的来源图；结合个人规模采取适度方案，不追求大型数据仓库能力。
- 将旧完整备份说明改为适合 D1 的导出/恢复演练说明；业务导出和包含身份/密钥配置的完整恢复分开说明。

最低验证范围：

| 场景 | 需核实的结果 |
| --- | --- |
| 收入/支出/转账/退款 | 金额、账户、分类、关联退款和统计正确 |
| 购物买入/放弃/撤销/补记账 | 清单、支出、物品、省钱关联完整，重复提交不重复写入 |
| 优惠与主动省钱 | 自动优惠、不买、降级来源可区分，删除/修改按原规则联动 |
| 物品成本与使用记录 | 按时间/次数正确计算，撤销使用可用 |
| 记录组、全部记账、预算结算 | 原有 P2 功能没有遗漏 |
| AI 文本与截图 | 结构校验、模块标签、时间保留、候选确认、失败恢复、图片不持久化 |
| AI 配置与额度 | 个人配置隔离、重复操作与失败释放正确，不泄漏密钥 |
| 批量操作 | 编辑/删除结果正确，相关失败不会留下半套数据 |
| 导入导出 | 往返一致，重复导入不重复，冲突与超限行为真实明确 |
| 购物评议 | 分享字段受限，人数与评语正常，其他用户无法访问私有账本 |
| 页面 | 首页组件自定义、模块草稿、桌面和390px手机布局均可用 |

复用并调整已有领域/服务/交换测试。数据库测试必须真正使用本地 D1 或其受支持模拟环境，不能继续只在 Prisma SQLite 上跑绿灯。失败回滚和重复提交保留少量关键用例，不增加没有需求的高并发压测。

### 阶段五：交付本地版本及部署说明

提供明确可运行的脚本，命名可以按工具调整，但至少覆盖：

- Cloudflare 目标构建。
- 本地 Workers 预览与本地 D1 初始化/迁移。
- 旧 SQLite 副本迁入本地 D1。
- 类型检查、lint、测试和面向 Workers 预览地址的 E2E。
- 以后部署时的远端迁移与部署命令（仅文档，不在本阶段执行）。

本地运行和测试默认只连本地 D1；远端命令显式标注，避免误执行。补全 `.env.example` / `.dev.vars.example` 等配置模板，真实配置加入忽略规则；D1 ID、binding 和秘密分别说明，不放真实密钥。

更新 README，说明账号创建后需要的最少步骤：创建 D1、填 binding、配置 secrets、备份后迁移数据、部署及冒烟验证。不要为了做文档要求用户先注册。

每阶段将完成项、实际执行命令、退出状态/测试数量、发现的问题及未验证事项写入 `docs/PROGRESS.md` 的 Cloudflare 专节。旧版 SQLite 的成功记录不可冒充 D1 验证结果。

交付时明确：

1. 哪个命令启动本地 Workers 版本。
2. 已迁移的数据范围与核对证据。
3. 使用的构建适配工具和数据库方案。
4. 截图不落盘、旧图片仍保留在原本地位置的行为。
5. 实际通过的检查与未验证事项。
6. 尚未部署云端，免费套餐的线上 CPU/网络表现仍需发布后验证。

## 6. 验收底线与不做事项

- 不改语言、不重做 UI、不用静态数据替代真实数据、不把不兼容功能悄悄删掉。
- 不再引入 Supabase 或截图对象存储，不维护 Vercel + D1 中转的双平台部署。
- 关键查询正确参数化；权限校验和秘密保护不因个人使用而取消。
- 不把 D1 batch 描述成能运行任意 JavaScript 事务回调。
- 本地 Workers 实际可用、核心业务在 D1 验证通过，才能称“本地迁移完成”。只有 `next build` 通过不算。
- 无账号/远端权限不阻塞本地实施；遇到真实工具兼容或安全登录障碍，如实记录具体问题，不能用收费服务或弱密码实现蒙混通过。
