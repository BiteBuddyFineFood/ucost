## 可复现的“升级 → 导出 → 新库导入 → 重启核对”

运行 `node scripts/verify-p4.mjs`，使用两个独立 SQLite 文件与不同进程，不操作当前用户库。脚本先只应用最初版结构并建立真实结构的脱敏合成样本，登记初始迁移后执行全部增量迁移。旧样本含：同名不同清单、已购关联账单/物品、已购无账单、部分退款、自动优惠待核对、用户主动停用省钱、账户期初、使用记录和草稿。

升级前后对比原始记录数、各类型账单合计、有效省钱，生成 anomaly 报告；未知金额保持待核对。随后在升级库加入预算采购：1000 元预算、两个不同日期物品共实付 800 元、其中优惠 50 元、整单有效省钱 200 元，以及部分确认草稿。导出 JSON v2 后在另一新库按不同用户导入，重复同一任务和文件，再启动第三个进程重新读取核对。

核对同时比较：所有实体数量、收入/支出/退款/净支出/有效省钱、逐账户期初和余额，以及全部引用字段（映射回源 ID）、分类图标、预算/实付快照、停用/替代状态、结算成员和已确认草稿索引。重启后另外修改原购买实付和优惠，确认更新同一条省钱记录，数量不增加。

最新成功证据目录由 `data/p4-verification/latest.json` 指向，包含：

- `upgrade-report.json`：旧结构升级前后不变和历史待核对明细。
- `export-v2.json`：仅脱敏合成业务数据。
- `expected.json`：源图及金额，按源 ID 归一化。
- `import-report.json`：新库导入数量、警告和前后金额。
- `roundtrip-report.json`：重启后的金额/来源图一致，以及购买修改不重复派生。
- `upgraded-source.db` / `new-destination.db`：可复核的两个隔离数据库。

该脚本不以构建结果代替财务验收。测试数据为合成脱敏样本；没有将用户真实记录发送到 AI。

## 安全升级与回退

1. 停止所有本项目 dev/start/测试写入进程，保存匹配版本的代码、`.env`、data 和 uploads。若数据库使用 WAL，必须停服务一起复制，或通过 SQLite 一致性备份 API；不要只在写入时复制 db 主文件。
2. `node scripts/verify-upgrade.mjs` 在当前库一致性备份副本与空库演练迁移，不修改源库。报告位于 `data/p2-p3-verification/migration-report.json`；这是沿用的历史目录名，报告包含本次 P4 迁移。
3. 确认副本核对通过，再执行 `npm.cmd run db:migrate` 和 `npm.cmd run db:generate`。Windows 引擎 DLL 被占用时先停相关 Next 服务。禁止 reset/drop 或用 db push 替代已有库迁移。
4. `node scripts/verify-upgrade.mjs --verify-current` 在尚无新业务写入时与升级前备份核对，随后重启服务，进入设置检查导入导出。生成客户端和首次迁移都不需要 AI 可用。
5. 往返迁移：源用户设置 → 全部 JSON v2；目标用户设置 → 选择文件 → 预检。分类同名时明确映射；其他组/清单/账户按源 ID 新增。确认新库金额、分组和来源后保留源库备份。
6. 回退时停止新服务，另外保全升级后的数据/附件和新增写入，再恢复升级前数据库、uploads、匹配代码和原 `.env`，重新生成对应客户端。不能让旧代码直接写入含新业务字段的库。若上线后已有新记录，先导出、核对恢复范围，不直接覆盖。
7. 项目现有 `.gitignore` 忽略 docs、README 和 `*.sql`。分发/提交须明确携带全部四份迁移、migration_lock.toml、格式说明和模板；不要只传 schema，也不要传真实数据库或导出。

## 明确边界

- CSV 是单模块交换，复杂结算、分类图标和完整来源迁移使用 JSON。
- 不恢复用户偏好/默认账户、登录态、AI 密钥和配额任务、公开分享资格或附件二进制。图片用完整数据库+uploads 备份恢复。
- 冲突“作为新记录”仍受来源唯一约束；自动优惠和预算结算不能借此复制一份有效金额。
- 没有对任意第三方 CSV 猜测列名；旧七列格式和 v2 模板有确定校验。超过单文件限制需要重新组织文件，预检不会悄悄部分导入。
- 此轮未验证真实手机语音硬件或真实外部 AI 语义，这不影响手动导入/导出及关联核对结果。
